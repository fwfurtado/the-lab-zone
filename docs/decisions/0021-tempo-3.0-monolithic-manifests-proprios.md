# ADR-0021 — Tempo 2.10.7 → 3.0 monolithic, gerido por manifests

## Status
Aceito. Migra o Tempo do chart Helm (app 2.10.7) para manifests próprios do app
3.0.2 em modo monolítico (`-target=all`).

## Contexto
Objetivo: estar up-to-date no Tempo. O chart `tempo` single-binary
(grafana-community, version 2.2.3) está **congelado no app 2.10.7** e injeta o flag
`-mem-ballast-size-mbs` hardcoded no StatefulSet — flag **removida no Tempo 3.0**,
que faz o pod recusar iniciar. Forçar `image.tag: 3.0.x` no chart não funciona.

Os caminhos avaliados:
- **Chart `tempo-distributed` 3.0.5**: existe, mas é MicroService mode — exige
  Kafka + ~12 componentes (distributor, querier, block-builder, live-store,
  backend-scheduler/worker, metrics-generator, memcached×N, gateway). Desproporcional
  para um homelab que roda hoje 1 pod de 1.5Gi.
- **Monolithic 3.0 (`-target=all`)**: roda tudo num processo, **sem Kafka** (o
  distributor empurra spans in-process pro live-store; durabilidade recente no WAL
  local). É o análogo direto do single-binary atual. Mas **nenhum chart** expõe esse
  modo no 3.0 (o `tempo` single-binary parou no 2.10.7; o SSB foi removido no upstream).

## Decisão
Gerir o Tempo 3.0.2 monolithic por **manifests próprios** (ConfigMap, StatefulSet,
Service, VMPodScrape), saindo do chart. O ExternalSecret `tempo-s3` (creds Garage)
é reaproveitado sem mudança.

Config 3.0 (breaking changes aplicados):
- `-mem-ballast-size-mbs` removido → `GOMEMLIMIT` (~80% do limit) via env.
- `compactor:` removido → compaction interna via `backend_scheduler`.
- `ingester:`/`ingester_client:` removidos (não existem no 3.0).
- overrides no formato **scoped** (`defaults:`) — o 3.0 recusa o formato flat.
- storage s3 Garage: **mesmo bucket** (cutover direto, sem 2.x concorrente → sem prefix).
- `-target=all`, receivers OTLP :4317/:4318, retention 168h — preservados.

Config validada com o **binário tempo 3.0.2 real**: parseia e inicializa o módulo
`store`; falha apenas ao conectar no Garage (esperado fora do cluster). Se houvesse
erro de schema (campo removido, overrides flat), falharia antes do connect.

## Cutover: DIRETO (in-place)
Decisão consciente de NÃO fazer convivência 2.x+3.x / rollout gradual:
- O 2.x tinha <1 semana de dados e retention de 7 dias → histórico rotaciona sozinho.
  Sem baseline longo, investigação em curso ou SLA a proteger.
- Homelab sem paginação: custo de um cutover falho é "sem traces por um tempo",
  não incidente. A maquinaria de dois Tempos (fan-out, prefix, dois datasources)
  protegeria dados que expiram em dias — custo > valor.

Rede de segurança mínima: **snapshot do bucket `tempo` no Garage antes de aplicar**.

O collector NÃO muda: o Service novo preserva o nome `tempo` e a porta :4317, então
o exporter `otlp/tempo` segue apontando pro lugar certo.

## Consequências
- **Sem downgrade in-place** 3.0→2.x (o 3.0 escreve blocos RF1 que o 2.x não lê).
  Abortar = restaurar snapshot do bucket + reverter manifests pro chart 2.10.7.
- **Nova responsabilidade**: acompanhar breaking changes de cada release do Tempo à
  mão (perdeu-se a abstração do chart). Trade-off aceito em troca de estar no 3.x.
- **Side-effect positivo**: TraceQL Metrics é GA no 3.0, servido pelo live-store — o
  Traces Drilldown (adiado no ADR anterior por exigir local-blocks) passa a funcionar
  de fábrica, sem generator. vParquet4 confirmado; sem migração de block format.
- Pré-requisito operacional: criar o item `garage-tempo` no 1Password se ainda não
  existir (o ExternalSecret já referencia).

## Gatilho de reavaliação
Se surgir um chart monolithic 3.x estável e mantido, reconsiderar voltar ao chart
para recuperar a abstração de upgrades.
